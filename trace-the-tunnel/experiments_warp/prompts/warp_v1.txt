You are running the v1 variant of the warp experiment on the browser
game at http://localhost:5050.

This is structurally identical to replay_v1b's in-page-dispatch strategy
(setTimeout + MouseEvent + dispatchEvent), with one change: the source
trajectory is sampled from a tunnel whose tunnel_id is DIFFERENT from
the live tunnel, and then warped onto the live tunnel's centerline
using arc-length matching and signed lateral offsets. The server's
/api/human_bank/<tunnel_id> endpoint is restricted to the same 30
disjoint source session_ids used by replay_v1b (3 per tunnel, 30
total), so any source we pick is guaranteed to be excluded from the
eval-time human distribution. The new /api/human_trace_full/<sid>
endpoint returns the source's control_points so we can reconstruct its
centerline. The cross-tunnel constraint is enforced inside the solver
(`window.__warp.pickSource`).

Do exactly the following, in order:

  1. browser_navigate to http://localhost:5050 and wait for the canvas
     to appear.

  2. Read experiments_warp/warp_solver.js with the Read tool.

  3. Inject its contents into the page via browser_evaluate. After this
     `typeof window.__warp` should be 'object'.

  4. Run all 10 tunnels with 3 attempts each:

       await window.__warp.runAll(3)

     For each tunnel the solver pools all 27 cross-tunnel candidates
     (3 per tunnel x 9 other tunnels) from the server bank and samples
     one per attempt.

  5. Report the per-tunnel state summary returned by the call. Include
     `source_session`, `source_tunnel`, and `n_outside` / `n_projected`
     fields if present. Do not fabricate numbers — only what runAll
     returned.
